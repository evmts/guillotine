# Guillotine

Guillotine is an Ethereum Virtual Machine written in Zig. It exists to make EVM
execution **fast**, **configurable at compile time**, and **embeddable** from
other languages through a C ABI (`src/evm_c_api.zig`).

:::warning[Alpha software]
Guillotine is early alpha and is **not suitable for production use**. It passes
all 66,652 official EEST state-test cases (Frontier through Osaka) but has had
no external audit. See [Project status](/status) for the measured numbers and
their sources.
:::

## Why another EVM?

Most EVMs are one implementation with runtime configuration. Guillotine takes a
different bet: the EVM is a **generic type parameterised by a comptime config
struct**, so the machine you get is specialised to exactly the semantics you
asked for, with the branches you don't need compiled away.

```zig
const Evm = @import("evm").Evm;

// The defaults: Osaka rules, gas metering, fusion, and precompiles.
const Mainnet = Evm(.{});

// A Berlin EVM with gas checks disabled, for a fuzzer that only cares about
// stack/memory semantics. The gas accounting code is not in the binary.
const eips = @import("evm").Eips;
const Fuzzing = Evm(.{
    .eips = eips{ .hardfork = .BERLIN },
    .disable_gas_checks = true,
});
```

That single design decision drives most of what is distinctive about the
codebase:

- **Dispatch-based execution, not a switch loop.** Bytecode is analysed once
  into a *dispatch schedule* of function pointers plus inline metadata, then
  executed by tail calls. There is no `switch (opcode)` on the hot path and no
  program counter in the frame. See [Dispatch](/concepts/dispatch).
- **Gas batched per basic block.** Analysis computes the static gas cost of a
  whole basic block, so the interpreter charges once per block instead of once
  per instruction.
- **Opcode fusion.** Common adjacent sequences (`PUSH1 n; MSTORE`,
  `ISZERO; PUSH; JUMPI`, a `PUSH` before a static `JUMP`) collapse into a single
  synthetic handler. See
  [Synthetic opcodes](/concepts/synthetic-opcodes).
- **A differential tracer built in.** Every handler can be validated in
  lock-step against `MinimalEvm`, a plain, readable, switch-loop reference
  interpreter that lives in the same repository. See [Tracing and
  debugging](/guides/tracing).

## Two EVMs, one repository

| | Performance EVM (`src/`) | `MinimalEvm` (`src/tracer/`) and guillotine-mini (`mini/`) |
| --- | --- | --- |
| Execution model | Dispatch schedule + tail calls | Sequential `switch` over bytecode |
| Optimised for | Throughput | Readability and correctness |
| Role | The product | Reference oracle for differential tests |
| Size | Whole `src/` tree | `minimal_evm.zig`, `minimal_frame.zig`, `minimal_host.zig`; `mini/` has its own `build.zig` |

They are not competitors. `MinimalEvm` is the thing that lets you *trust* the
fast one: the tracer steps both machines forward together and asserts they agree
on stack, memory, gas, and storage after every instruction.

## Relationship to the rest of the stack

Guillotine is the execution engine at the bottom of the Tevm stack. If you are
trying to work out whether you want this repository, Tevm, ZEVM, Voltaire, or
guillotine-mini, read [The stack](/stack) first. It is a two-minute page that
will save you an afternoon.
