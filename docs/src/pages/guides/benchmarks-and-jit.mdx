# Benchmarks and native JIT

Guillotine ships **two benchmark suites** directly inside `bench/`:

1. **Cross-EVM apples-to-apples suite (`bench/compare/`)**: in-process,
   differentially verified comparison against **`alloy-rs/evm2`**,
   **`bluealloy/revm`**, **`ipsilon/evmone`** (Advanced & Baseline),
   **`lambdaclass/ethrex`** (LEVM), **`Giulio2002/gevm`**,
   **`ethereum/go-ethereum`** (`geth`), and Tier 2 native JIT compilers
   (**`evm2-jit`** LLVM 23, **`revmc`** LLVM 22, **`guillotine-jit`**).
2. **In-repo ReleaseFast runner (`zig build bench`)**: self-contained micro- and
   contract-benchmark suite for tracking opcode, precompile, and contract
   regressions without external checkouts.

The repository also contains a zero-dependency ARM64 JIT library under
`src/jit/`.

## Cross-EVM apples-to-apples benchmarks (`bench/compare/`)

Legacy cross-EVM benchmarks often suffer from CLI process-spawn overhead (e.g.
wrapping 1 transaction in `hyperfine`), unverified outputs, mixed warm/cold
caching, or cherry-picked synthetic loops. `bench/compare/` is engineered so
every number is directly auditable and reproducible from this repository.

### Methodology & fairness guarantees

- **Zero CLI startup overhead:** Every engine runs **in-process** inside its own
  compiled native binary (`zig-out/bin/guillotine-compare`,
  `bench/compare/bin/compare-*`) with a monotonic clock wrapping only EVM
  transaction execution.
- **Public, non-cherry-picked fixtures:** 21 of 25 workloads are pulled verbatim
  from [`alloy-rs/evm2`](https://github.com/alloy-rs/evm2) (`e80df9c46a82`,
  classic compute benchmarks, real Mainnet DeFi contracts, and precompiles),
  plus 4 targeted hot-loop workloads (`loop_arithmetic`, `loop_memory`,
  `loop_storage`, `loop_staticcall`).
- **0-tolerance differential verification gate:** Every timed sample on every
  engine must pass `success == true`, **exact `gas_used`** (0-gas tolerance),
  and **byte-for-byte `output`** match against canonical consensus. Any engine
  that diverges is disqualified (`MISMATCH`) rather than timed.
- **Warm vs. Cold separation:**
  - **Warm steady-state:** Bytecode is pre-loaded/analyzed where supported; each
    measured transaction starts from an identical clean pre-state snapshot (no
    state accumulation across iterations).
  - **Cold first-run:** Every sample builds a fresh EVM from raw unanalyzed
    bytecode with empty jumpdest/dispatch caches.
- **Strict JIT tier separation:** Native LLVM/AArch64 compilers are reported in
  their own Tier 2 table showing **both** one-time compile latency and warm
  execution latency, and explicitly flagging interpreter fallbacks.
- **Comparable native optimization flags:** Zig `-OReleaseFast` (native CPU),
  Rust `opt-level=3`, `lto=thin`, `codegen-units=1`, `panic=abort`,
  `-C target-cpu=native`, C++ `evmone` `-O3 -mcpu=native` + `libsecp256k1`, Go
  1.26 default release builds.
- **Geometric means:** Category and overall ratios use geometric means of
  per-workload speedups so a single long contract (`snailtracer`) cannot swamp
  the rest of the suite.

### Tradeoffs, cold analysis, and Tier 2 JITs

The full report intentionally exposes where Guillotine excels and where it still
trails:

- **Compute & opcode fusion wins:** Guillotine is the **fastest interpreter** in
  Classic compute (`1.43×` vs `revm`, `1.30×` vs `evm2`) and on heavy Mainnet
  compute (`burntpix` `1.86×` vs `revm`, `uniswap_v3_pool` `1.70×` vs `revm`,
  `curve_stableswap` `1.16×` vs `revm`). Turning fusion off drops overall
  geomean from `1.00×` to `0.89×` (`burntpix` slows `2.01×`, `snailtracer`
  slows `1.66×`).
- **Precompile gap (`0.61×` vs `revm`):** Pure-Zig `ECRECOVER` (`177.48 µs` vs
  ~`30 µs` `libsecp256k1` in `evm2`/`revm`/`evmone`/`gevm`) and
  `BN254_PAIRING` (`1.22 ms` vs `628 µs` in `evm2`) are the main drag on
  overall geomean. `MODEXP` (`1.81 ms`) beats `revm` (`2.42 ms`) by `1.33×`.
- **Storage & call loops:** `loop_storage` (`113.73 µs` vs `70.58 µs` `evm2`)
  and `loop_staticcall` (`84.04 µs` vs `56.19 µs` `evm2`) show headroom in
  journal/state lookup and nested frame setup.
- **Cold first-run (`0.27×` vs `revm`):** Building a full dispatch schedule with
  fusion passes takes `300–800 µs` on large uncached Mainnet contracts
  (`seaport` `800.67 µs` cold → `2.08 µs` warm; `uniswap_v3_pool` `792.63 µs`
  cold → `11.40 µs` warm), whereas simple jumpdest-bitmap interpreters analyze
  in `1–25 µs`. On compute-heavy workloads like `snailtracer` (`56.94 ms` cold)
  and `burntpix` (`38.83 ms` cold), Guillotine still finishes #1 even cold.
- **Tier 2 LLVM JITs (`evm2-jit` LLVM 23 & `revmc` LLVM 22):** Paying a
  one-time compile cost (`10 ms–8.5 s` depending on contract size) brings
  `snailtracer` down to `19.31–20.31 ms` and `burntpix` down to `7.60–8.80 ms`.
  In `v0.1.0`, Guillotine's `src/jit/` is not yet wired into `Evm`, so
  `guillotine-jit` transparently executes on the interpreter (`interp fallback`).

### Reproducing the cross-EVM suite

```bash
# 1. Fetch pinned workloads & compile all native runners
./bench/compare/build-all.sh

# 2. Run warm + cold + jit modes sequentially on an idle machine
node bench/compare/run.mjs

# 3. Filter to specific workloads or engines
node bench/compare/run.mjs --filter snailtracer,burntpix --modes warm,jit
node bench/compare/run.mjs --modes warm --engines guillotine,evm2,revm,evmone-baseline
```

Outputs are written to `bench/compare/RESULTS.md` (Markdown report),
`bench/compare/report.html` (self-contained interactive HTML report), and
`bench/compare/results/latest.json` (gitignored full dataset with raw samples
and environment provenance). See `bench/compare/README.md` for pinned revisions
and platform notes (including why `category-labs/monad` requires Linux x86-64-v3).

### Running the in-repo benchmarks

Run every command from the repository root with Zig 0.17.1. The runner builds
the EVM and its dependencies in ReleaseFast and refuses timing runs in any other
optimization mode.

```bash
# Full suite from the root build (Osaka, 16,777,216 gas budget)
zig build bench

# Filter and set sample and warmup counts
zig build bench -- --filter opcode/ADD --iterations 1000 --warmup 100

# Write JSON (default bench/results/latest.json)
zig build bench -- --json bench/results/latest.json

# Contract fixtures such as snailtracer need Prague's 1B off-chain budget;
# -Dbench-hardfork is an option of the standalone bench/build.zig
zig build --build-file bench/build.zig bench -Dbench-hardfork=PRAGUE -- --filter contract/

# Harness tests
zig build test-bench
```

`zig build bench-build` installs `zig-out/bin/guillotine-bench`;
`zig build bench-compare-build` installs `zig-out/bin/guillotine-compare`.

:::info[Hardfork and gas budget]
Benchmarks default to Osaka with EIP-7825's 16,777,216 transaction gas cap.
Snailtracer consumes about 235M gas per call, so contract runs use
`-Dbench-hardfork=PRAGUE` (1B off-chain budget). `CLZ` and `P256VERIFY` require
Osaka and are reported as unavailable on Prague.
:::

### What a sample measures

- Each sample times `evm.simulate()`: the ephemeral state overlay, dispatch
  analysis, execution, and owned result copying. Deployment, preflight
  validation, warmups and result cleanup are outside the timed window.
- Every sample must succeed and match the preflight gas and output. Failed or
  unavailable cases never receive timing numbers.
- `--compare` reports the loop-dispatch row as `unavailable`, because the engine
  always uses tail-call dispatch.

`bench/README.md` documents the workloads, the JSON schema and the statistics.

## Native ARM64 JIT library

`src/jit/` compiles side-effect-free EVM bytecode directly to AArch64 machine
code. It depends only on Zig `std` and `builtin`: no LLVM and no external
assembler at runtime.

:::warning[Not wired into `Evm`]
In v0.1.0 the JIT is a library with its own tests. `Evm` and `EvmConfig` do not
call it, so contracts always run on the dispatch-schedule interpreter. Run its
tests with `zig build test-jit`; native code executes only on `aarch64` (CI
runs the step on `macos-latest`).
:::

| File | Role |
| --- | --- |
| `src/jit/root.zig` | Public types (`JitContext`, `ExitCode`, `RuntimeHelpers`) and the test root |
| `src/jit/compiler.zig` | EVM-to-AArch64 compiler (`Program`, `Options`, `compile`) |
| `src/jit/arm64_emitter.zig` | AArch64 instruction encoder |
| `src/jit/x86_64_emitter.zig` | x86_64 instruction encoder; `compile` returns `null` unless `builtin.cpu.arch == .aarch64` |
| `src/jit/jit_mem.zig` | Executable page mapping (`MAP_JIT` with per-thread `pthread_jit_write_protect_np` toggling on macOS) |
| `src/jit/jit_cache.zig` | Bounded LRU cache (`capacity = 64`, `hot_threshold = 2`) |

### Eligibility and fallback

- **Supported:** arithmetic, bitwise, comparison and stack operations, memory
  (`MLOAD`, `MSTORE`, `MSTORE8`, `MSIZE`, `MCOPY`), calldata reads, control flow
  (`JUMP`, `JUMPI`, `JUMPDEST`, `PC`, `GAS`), `KECCAK256`, `STOP`, `RETURN` and
  `REVERT`.
- **Ineligible:** storage, logs, calls and `CREATE`/`CREATE2`. `compile`
  returns `null` for such code.
- **Fallback:** a JIT run has no external side effects. When it returns
  `ExitCode.fallback`, or `compile` returns `null`, the host re-executes the
  whole call in the interpreter with identical results.
- **Safety:** compiled code checks stack bounds against a 1,024-word stack, and
  `JitContext.instruction_budget` defaults to 300,000,000.
