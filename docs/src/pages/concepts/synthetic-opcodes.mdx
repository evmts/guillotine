# Synthetic opcodes

A synthetic opcode is a handler that performs the work of several real opcodes in
one dispatch step. Solidity emits highly repetitive bytecode; fusing the common
sequences removes dispatch overhead without changing semantics or gas.

```
Original:   PUSH1 0x20, MSTORE      2 handlers + 2 metadata items
Fused:      PUSH_MSTORE_INLINE      1 handler  + 1 metadata item
```

Gas is unchanged. The fused handler charges what the constituent opcodes would
have charged, and the basic-block gas header already accounts for them together.

## The set

Defined in `src/opcodes/opcode_synthetic.zig` as an `enum(u8)` occupying the
`0xA5`–`0xCF` range (unused by real EVM opcodes). Verified against the source:

### PUSH + arithmetic

| Synthetic | Value | Fuses |
| --- | --- | --- |
| `PUSH_ADD_INLINE` | `0xA5` | `PUSH` (value fits in 64 bits) + `ADD` |
| `PUSH_ADD_POINTER` | `0xA6` | `PUSH` (value wider than 64 bits) + `ADD` |
| `PUSH_MUL_INLINE` | `0xA7` | `PUSH` + `MUL` |
| `PUSH_MUL_POINTER` | `0xA8` | `PUSH` + `MUL` |
| `PUSH_DIV_INLINE` | `0xA9` | `PUSH` + `DIV` |
| `PUSH_DIV_POINTER` | `0xAA` | `PUSH` + `DIV` |
| `PUSH_SUB_INLINE` | `0xAF` | `PUSH` + `SUB` |
| `PUSH_SUB_POINTER` | `0xB0` | `PUSH` + `SUB` |

### PUSH + memory

| Synthetic | Value | Fuses |
| --- | --- | --- |
| `PUSH_MLOAD_INLINE` | `0xB1` | `PUSH` offset + `MLOAD` |
| `PUSH_MLOAD_POINTER` | `0xB2` | `PUSH` offset + `MLOAD` |
| `PUSH_MSTORE_INLINE` | `0xB3` | `PUSH` offset + `MSTORE` |
| `PUSH_MSTORE_POINTER` | `0xB4` | `PUSH` offset + `MSTORE` |
| `PUSH_MSTORE8_INLINE` | `0xBB` | `PUSH` offset + `MSTORE8` |
| `PUSH_MSTORE8_POINTER` | `0xBC` | `PUSH` offset + `MSTORE8` |

### PUSH + bitwise

| Synthetic | Value | Fuses |
| --- | --- | --- |
| `PUSH_AND_INLINE` / `PUSH_AND_POINTER` | `0xB5` / `0xB6` | `PUSH` + `AND` |
| `PUSH_OR_INLINE` / `PUSH_OR_POINTER` | `0xB7` / `0xB8` | `PUSH` + `OR` |
| `PUSH_XOR_INLINE` / `PUSH_XOR_POINTER` | `0xB9` / `0xBA` | `PUSH` + `XOR` |

### Jumps

| Synthetic | Value | Fuses |
| --- | --- | --- |
| `JUMP_TO_STATIC_LOCATION` | `0xBD` | `PUSH` + `JUMP` with the target resolved at analysis time |
| `JUMPI_TO_STATIC_LOCATION` | `0xBE` | `PUSH` + `JUMPI` with the target resolved at analysis time |

### Three-opcode patterns

| Synthetic | Value | Fuses |
| --- | --- | --- |
| `ISZERO_JUMPI` | `0xC3` | `ISZERO` + `PUSH` + `JUMPI` |
| `PUSH_ADD_DUP1_INLINE` | `0xCB` | `PUSH` + `ADD` + `DUP1`, push value fits in 64 bits |
| `PUSH_ADD_DUP1_POINTER` | `0xCC` | `PUSH` + `ADD` + `DUP1`, push value wider than 64 bits |

### Block markers

| Synthetic | Value | Purpose |
| --- | --- | --- |
| `BLOCK_BEGIN` | `0xCE` | Basic block entered by falling through a non-taken `JUMPI`; charges the block's gas |
| `INVALID_JUMP_TARGET` | `0xCF` | Target of a static jump whose destination is not a `JUMPDEST` |

The analyzer marks a fusion candidate only at `PUSH` followed by `ADD`, `MUL`,
`SUB`, `DIV`, `AND`, `OR`, `XOR`, `MLOAD`, `MSTORE`, `MSTORE8`, `JUMP` or
`JUMPI`, and at `ISZERO` + `PUSH` + `JUMPI`. Thirteen older synthetic opcodes
that no candidate could reach (`MULTI_PUSH_2/3`, `MULTI_POP_2/3`,
`DUP2_MSTORE_PUSH`, `DUP3_ADD_MSTORE`, `SWAP1_DUP2_ADD`, `PUSH_DUP3_ADD`,
`FUNCTION_DISPATCH`, `CALLVALUE_CHECK`, `PUSH0_REVERT`, `MLOAD_SWAP1_DUP2`,
`BACKWARD_LOOP_JUMPI`) were deleted, so their values are unused.

## Inline vs pointer

A fused handler's operand is one schedule item. When the pushed value fits in a
`u64`, the item is `push_inline` and holds the value. A wider value lives in the
schedule arena and the item is `push_pointer` (`handleFusionOperation` in
`src/preprocessor/dispatch.zig`). Two variants exist so the common path never
pays for an indirection.

A plain `PUSH1`–`PUSH32` never uses a pointer: the schedule stores its value as
one to four inline 64-bit limbs, least significant first (`processPushOpcode`).

## Turning fusion off

Fusion is on by default. It is the comptime `EvmConfig.enable_fusion` field, so
you can compare:

```zig
const Fused   = @import("evm").Evm(.{ .enable_fusion = true });
const Unfused = @import("evm").Evm(.{ .enable_fusion = false });
```

`-Devm-enable-fusion=false` sets the same field for the build-configured EVM
(`DefaultEvm` in `src/root.zig`) and for the `zig build state-tests` runner. CI
runs the official state tests both ways.

Turning it off is the first thing to try when a contract behaves differently from
another EVM. If the difference disappears, you have found a fusion bug. Please
file it.

## Fusion and the differential tracer

This is where synthetic opcodes interact with testing. `Frame` executes one fused
handler; `MinimalEvm` must execute *all* the underlying opcodes to stay in sync.
The tracer knows the arity of each synthetic opcode and steps the reference
machine the right number of times:

| Frame executes | MinimalEvm steps |
| --- | --- |
| A real opcode | 1 |
| `PUSH_MSTORE_INLINE` | 2 (`PUSH1`, `MSTORE`) |
| `ISZERO_JUMPI` | 3 (`ISZERO`, `PUSH`, `JUMPI`) |

That mapping lives in `getMaxStepsForOpcode()`, called by
`executeMinimalEvmForOpcode()` in `src/tracer/minimal_evm_sync.zig`.
A "divergence" that turns out to be an arity mismatch there is a tracer bug, not
an EVM bug. Check the arity before you suspect the handler.
