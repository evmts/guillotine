# Dispatch

Guillotine does not interpret bytecode. It compiles bytecode into a **dispatch
schedule** and then executes the schedule as a chain of tail calls.

If you read only one concept page before touching `src/frame/`, read this one.
Almost every confusing bug report about Guillotine comes from assuming the frame
has a program counter.

## The traditional shape

A conventional interpreter, including Guillotine's own `MinimalEvm` reference,
looks like this:

```zig
while (self.pc < self.bytecode.len) {
    const opcode = self.bytecode[self.pc];
    switch (opcode) {
        0x01 => { // ADD
            const b = self.popStack();
            const a = self.popStack();
            self.pushStack(a +% b);
            self.pc += 1;
        },
        // ... 255 more cases
    }
}
```

Every instruction pays for: an unpredictable 256-way indirect branch, a bytecode
memory read, a bounds check, a gas check, and stack-depth validation.

## The dispatch shape

```zig
// src/frame/frame.zig
pub const OpcodeHandler = *const fn (frame: *Self, cursor: [*]const Dispatch.Item, sp: [*]WordType, gas: GasType, t0: u64, t1: u64, t2: u64, t3: u64) callconv(handler_abi.handler_cc) handler_abi.ExitCode;
```

Every handler has this signature (`src/preprocessor/handler_abi.zig`). It ends by
tail-calling the next handler, so a contract's whole execution is one native
stack frame deep. On LLVM x86_64 and aarch64, `handler_cc` is `preserve_none`:
the four arguments stay pinned in registers across the handler chain. That
calling convention cannot return an error union or take a `u256` by value, so a
handler returns an `ExitCode` and the caller maps it back to an error with
`errorFromExit`. Other targets use the C calling convention.

`sp` and `gas` are the live stack pointer and gas counter. `t0..t3` are the top stack
item as 64-bit limbs; `sp[0]` is its spill slot and `sp[1]` is the second item.
`frame.stack.stack_ptr`, the word at `sp[0]` and `frame.gas_remaining` are stale while
handlers run.

```zig
// src/instructions/handlers_arithmetic.zig
pub fn add(self: *FrameType, cursor: [*]const Dispatch.Item, sp: [*]WordType, gas: FrameType.GasType, t0: u64, t1: u64, t2: u64, t3: u64) callconv(handler_abi.handler_cc) handler_abi.ExitCode {
    var s = N.StackView.init(sp, t0, t1, t2, t3);
    N.before(self, .ADD, cursor, s, gas);

    s.binary_op_unsafe(struct {
        fn op(top: WordType, second: WordType) WordType {
            return top +% second;
        }
    }.op);

    return N.next(self, .ADD, cursor, s, gas);
}
```

`N` is `handler_abi.Native(FrameType)`. In Debug and ReleaseSafe builds, and
whenever the tracer is compiled in, `N.before` writes `sp` and `gas` back to the
frame and calls `frame.beforeInstruction`; otherwise it compiles to nothing.
`N.next` looks up the next handler and cursor, calls `afterInstruction` under
the same condition, and tail-calls the next handler. Handlers dominated by host
work (storage, calls, logs) are written as step functions and adapted with
`handler_abi.wrap`.

## The schedule

A schedule is a flat array of `Item`: a handler pointer, or one word of
metadata for the handler before it.

```zig
// src/preprocessor/dispatch.zig
pub const Item = if (item_tagged) union(enum) {
    opcode_handler: OpcodeHandler,
    jump_dest: Metadata.JumpDestMetadata,
    push_inline: Metadata.PushInlineMetadata,
    push_pointer: Metadata.PushPointerMetadata,
    pc: Metadata.PcMetadata,
    jump_static: Metadata.JumpStaticMetadata,
    first_block_gas: Metadata.FirstBlockMetadata,
} else extern union { ... same fields ... };
```

`item_tagged` is true in Debug and ReleaseSafe builds and whenever the tracer is
compiled in, so the schedule can be validated item by item. Every other build
uses the untagged `extern union`, and a comptime check holds it to 8 bytes.

For the bytecode `PUSH1 0x01, PUSH1 0x02, ADD, STOP`:

```
Bytecode:  [0x60, 0x01, 0x60, 0x02, 0x01, 0x00]
PC:           0     1     2     3     4     5

Schedule:
Index  Item                Payload
─────  ──────────────────  ─────────────────────────────────────────
[0]    first_block_gas     { gas: 9, min_stack: 0, max_stack: 2 }
[1]    opcode_handler      → push1 handler
[2]    push_inline         { value: 1 }
[3]    opcode_handler      → push1 handler
[4]    push_inline         { value: 2 }
[5]    opcode_handler      → add handler
[6]    opcode_handler      → stop handler
[7]    opcode_handler      → stop handler (implicit STOP at end of code)
[8]    opcode_handler      → INVALID_JUMP_TARGET handler
[9]    opcode_handler      → stop handler
[10]   opcode_handler      → stop handler
```

The builder always appends items 7 to 10: an implicit `STOP` for code that runs
off its end, the target for static jumps to a non-`JUMPDEST`, and two `STOP`s
that end every schedule. The example assumes `EvmConfig.enable_fusion = false`.

### Push values

The schedule stores a `PUSH1`–`PUSH32` value as one to four inline 64-bit limbs
after the handler, least significant first: one for `PUSH1`–`PUSH8`, two for
`PUSH9`–`PUSH16`, three for `PUSH17`–`PUSH24`, four for `PUSH25`–`PUSH32`
(`pushLimbCount` and `processPushOpcode` in `src/preprocessor/dispatch.zig`).
The push handler rebuilds the word from the schedule and never reads the
original bytecode.

Fused handlers take one operand item instead. A value that fits in a `u64` is a
`push_inline` item; a wider value lives in the schedule arena and is reached
through a `push_pointer` item. See [Synthetic opcodes](/concepts/synthetic-opcodes).

## Cursor ≠ PC

**The cursor is an index into the schedule. It is not a program counter.**

```
Bytecode PC:      0   1   2   3   4   5
Schedule index:   0   1   2   3   4   5   6
                  ▲
                  └── metadata, corresponds to no opcode at all
```

Consequences you must internalise:

1. `schedule[0]` is usually `first_block_gas`, so the first *instruction* is at
   index 1.
2. A single synthetic item can stand for several bytecode operations, so schedule
   indices drift further from PCs as you go.
3. Jump targets stored in `jump_static` are **schedule indices**, resolved at
   analysis time, so a static `JUMP` costs no lookup at runtime.
4. `PC` is still implementable because analysis stores the true bytecode offset in
   a `pc` metadata item for exactly the opcodes that need it.

## Gas is batched per basic block

Analysis splits code at every `JUMPDEST` and every terminating or branching
instruction. Each block gets a `FirstBlockMetadata` / `JumpDestMetadata` header
carrying the block's total static gas cost and its stack-height requirements.

The interpreter charges the whole block's gas and validates stack height **once,
on entry to the block**. Inside the block, handlers use `_unsafe` stack
operations and do no gas arithmetic at all, except for genuinely dynamic costs
(memory expansion, `SSTORE` refunds, call gas forwarding, `EXP` exponent bytes,
copy costs).

This is the single biggest reason handlers look so short.

## Static jump resolution

```
JUMP where the destination came from a PUSH the analyser can see
    → resolved to a schedule index at analysis time (jump_static)
    → runtime cost: set cursor, tail call

JUMP where the destination is computed at runtime
    → runtime lookup in the jump table, validated against the JUMPDEST bitmap
```

## Schedule caching

Schedules are cached per contract in the EVM's dispatch cache, so a contract
called repeatedly in a transaction (or across transactions on the same `Evm`) is
analysed once. Analysis is the expensive part; execution is cheap.

## What this means for you

- **Writing a handler?** It must call `N.before(self, opcode, cursor, s, gas)`
  first and end with `N.next(...)`, or the differential tracer desynchronises and tests fail with confusing
  state mismatches. See [Tracing](/guides/tracing).
- **Debugging?** Print the schedule, not the bytecode:
  `@import("evm").dispatch_pretty_print.pretty_print(...)` or the C export
  `evm_dispatch_pretty_print`.
- **Benchmarking?** Make sure the schedule is warm. A cold first call includes
  analysis.
