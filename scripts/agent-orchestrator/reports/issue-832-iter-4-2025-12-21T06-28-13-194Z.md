## What I Found
- The database.zig already has an ephemeral overlay system for simulation
- Transactions use snapshot mechanism which clones entire state (expensive for rollback)
- The `set_code` operation allocates from main allocator during transaction execution
- Memory fragmentation occurs because temporary allocations during transactions become permanent

## What I Changed
Implemented transaction-level caching with arena allocator in `src/storage/database.zig`:

1. **Added `TransactionCache` struct** (lines 93-155):
   - Uses `std.heap.ArenaAllocator` for O(1) cleanup on rollback
   - Contains cached accounts, storage, and code hashmaps
   - All allocations from arena are automatically freed when cache is destroyed

2. **Added `tx_cache` field to Database** (line 172):
   - Optional pointer to active transaction cache

3. **Updated get/set operations** to check transaction cache:
   - `get_account`, `set_account`, `delete_account`, `account_exists`
   - `get_storage`, `set_storage`
   - `get_code`, `set_code`, `get_code_by_address`

4. **Enhanced transaction operations**:
   - `begin_transaction`: Now initializes arena-backed transaction cache
   - `commit_transaction`: Flushes cache to permanent storage, then commits snapshot
   - `rollback_transaction`: Simply destroys arena (O(1)), then reverts snapshot

5. **Added standalone cache operations**:
   - `begin_tx_cache()`: Start caching without snapshot
   - `commit_tx_cache()`: Flush cache without snapshot management
   - `rollback_tx_cache()`: O(1) discard of cache
   - `has_tx_cache()`: Check if cache is active

6. **Added comprehensive tests** (lines 2649-2889):
   - Basic account buffering
   - O(1) rollback with many changes
   - Storage buffering
   - Code storage buffering
   - Standalone cache operations
   - Account deletion buffering
